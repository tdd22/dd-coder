# 按教程升级 dd-coder

用户写功能。助手核对文件、在分叉处提问，并按下面的回复形状带用户走。用户说「测试你来做」或「你改就行」时，才补测试、改笔误、更新 `docs/DEVELOPMENT.md`。

## 开始之前

1. 读 `docs/DEVELOPMENT.md` 和该章的 `learn-workbuddy/<chapter>/README.md`。
2. 把章节机制接到现有的 LangGraph 图和工具注册表上。
3. 保留已经定下的决定：读直接执行，写入和命令先询问，多条会话靠 `thread_id`。不要恢复已删除的 `agent/loop.py`。教程里的 `for` 循环、单一 bash、另一套确认按钮，不要拿来替换现有的图和 `interrupt`。

## 设计

有真实分叉时，一次只问一个问题，并给出推荐。用户选定后，用一段短设计说明改哪些文件、哪些行为不变。用户确认后再进入讲解。

## 每一次回复只做一件事

先看用户最后一句，选一种回复。不要把两种混在同一条消息里。

**还没选定或还没确认设计：** 只提问，或只给短设计。不给待贴代码。

**用户说看不懂、绕、或问「这段在干什么」：** 只用一个具体例子把调用顺序讲完，然后停住。例子里要有真实输入（一两行日志、一次工具调用，或一条请求），并写出每一步之后磁盘或图状态变成什么。不附带下一步要贴的代码，也不引用大段新代码。

**用户要看现有实现「怎么写的」：** 按调用顺序引用仓库里已经存在的代码，指出每个函数返回后谁接着跑。不新增待贴代码。

**用户说「我懂了」：** 停住。用一两句确认刚才的例子，并说明要说「继续」才进入下一步。这不是「好了」。

**用户说「继续」，或说「好了」且文件已经读过：** 先讲这一小步，再给代码。顺序固定：

1. 它在整条链路的哪一步，前一步已经留下什么。
2. 按执行顺序写出这一小步做的事。每一步都要能对上后面代码里的一个判断或一次写盘。
3. 用一个具体输入走完，写出这一步结束时文件或返回值是什么样。
4. 写明这一步先不做什么。
5. 给一段能粘贴的代码，并且这段代码只实现刚讲过的那一层。代码里的每个新名字都要在前面的例子里出现过。

## 拆开

一个新名字、一条新规则，或一个新函数，算一步。同一条规则要用例子讲过，才能出现在待贴代码里。

用户回复「好了」之后，先读文件里的实际内容，再给下一步。下一步之前先指出：缩进错误、`false` 写成了 `False`、中文标点、循环体内提前执行、方法写在类外面、多出来的缩进导致文件无法导入。

## 收尾

只在用户交出测试或修改时：

- 补不请求模型的测试，并跑上一章已经有的测试。
- 把新行为写入 `docs/DEVELOPMENT.md`。
- 会话里要跨提问保留的状态，不要在每次 `invoke` 的输入里重置。`turns` 每次从 0 开始；`loaded_tools` 这种名单要留着。

## 常见借口

| 借口 | 实际情况 |
| --- | --- |
| 一句前言加上整段函数，就算讲过链路了 | 前言没有写出每一步之后状态变了什么，用户仍然不知道代码在干什么 |
| 用户说继续，所以这段直接给代码 | 「继续」只表示上一段懂了。这一小步仍要先讲，再给只实现这一层的代码 |
| 设计里说过了，代码不用再讲 | 设计是整章。这一小步的输入、判断和写盘结果要单独讲 |
| 看不懂时把下一块代码附上，方便对照 | 看不懂时只有例子。代码留到用户说「继续」 |
| 「我懂了」等于「好了」 | 「我懂了」只结束讲解。文件改完才是「好了」，要先读文件 |
