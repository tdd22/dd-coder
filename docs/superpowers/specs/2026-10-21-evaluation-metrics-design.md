# dd-coder 评测指标体系设计

## 目标

为 dd-coder 建立面向研发回归的 SWE-bench Lite 评测体系。它需要回答三个问题：

1. 候选版本是否比固定基线修复了更多实例，且没有引入严重违规？
2. 结果变化来自哪里：任务结果、Agent 过程、成本，还是评测基础设施？
3. 哪些变化值得人工复核？

首版每个实例、每个配置只运行一次。系统不能把单次随机波动包装成统计确定性；关键结果翻转应作为暂定证据并进入复跑或人工复核队列。

## 范围

首版只覆盖 SWE-bench Lite 自动修复任务，以官方 evaluator 作为修复正确性的唯一裁判。

首版包含：

- 确定性的结果、门禁、过程和成本指标；
- 非数字性的质量标签；
- 固定基线与候选版本的逐题配对比较；
- LLM-as-judge 初审和人工抽查；
- 可复现性元数据。

首版不包含：

- pass@k、跨重复运行方差或成功概率校准；
- 把所有维度压成一个加权总分；
- 用 LLM judge 取代官方 evaluator；
- 与明确风险无关的主观代码美观度评分。

## 设计原则

### 分层而非总分

指标分为结果、硬门禁、诊断与效率、定性质量四层。低 token 或低耗时不能抵消错误修复、测试篡改或工作区越界。

### 确定性不等于数字

`失败阶段=补丁未生成` 是确定性分类标签。指标模型同时允许布尔值、数字、枚举和带证据的定性标签。

### 结果与过程分开

官方测试决定“是否修好”；过程指标解释“如何完成或为何失败”。过程看起来合理不能把失败实例判为成功。

### Agent 失败与基础设施失败分开

仓库克隆失败、评测容器异常或 evaluator 崩溃记为 `infra_error`，不计作 Agent 修复失败，也不进入效率比较。

### 单次运行保留不确定性

每题只跑一次时，改善结论标记为暂定。系统允许输出“无法判断”，并保留 outcome flip 实例供定向复跑。

## 指标分层

### 结果层

结果层是回归判断的核心：

- `eval_status`：`completed`、`infra_error`、`agent_error` 或 `timeout`；
- `resolved`：官方 evaluator 是否判定实例解决；
- `fail_to_pass_passed` 与 `fail_to_pass_total`；
- `pass_to_pass_passed` 与 `pass_to_pass_total`；
- `patch_generated`：是否产生非空补丁；
- `patch_applied`：补丁是否成功应用；
- `regression_introduced`：是否有 PASS_TO_PASS 测试由通过变为失败。

只有 `eval_status=completed` 的实例可以进入模型结果比较。

### 硬门禁层

门禁记录不可被其他指标抵消的严重问题：

- `modified_tests`：修改了任务测试或测试夹具；
- `modified_forbidden_paths`：修改 evaluator、benchmark harness 或其他禁止路径；
- `workspace_escape`：写入工作区外；
- `gold_leak_detected`：读取或利用 gold patch、隐藏测试答案等禁止信息；
- `evaluation_tampering`：试图绕过或篡改评分；
- `empty_patch`：正常结束但没有有效补丁；
- `patch_apply_failure`：补丁不能应用。

门禁应保存布尔结果、命中规则和证据位置。规则未执行时必须记为 `not_evaluated`，不能默认为通过。

### 诊断与效率层

首版必须收集：

- Agent 轮数；
- 各工具调用次数和工具调用总数；
- 工具失败次数；
- 完全相同命令的额外重复次数；
- 测试命令总数、成功数和失败数；
- 输入 token、输出 token 和估算费用；
- 端到端耗时；
- stop reason；
- 补丁文件数、增加行数和删除行数；
- 是否包含二进制文件或异常大文件。

第二阶段可增加：

- 首次有效编辑耗时；
- 首次相关测试耗时；
- 对同一代码区反复编辑或回滚的次数；
- 无效读取、重复搜索和无进展轮数；
- 上下文压缩次数、峰值上下文和大结果外置次数；
- 聚焦测试与全量测试的选择顺序；
- 失败根因分类。

次数指标必须定义清楚计数单位。例如“重复命令”是同一规范化命令在首次执行之后的额外执行次数，而不是出现过重复的命令种类数。

### 定性质量层

LLM judge 对以下维度输出枚举标签，不输出伪精确的数字分数：

- `problem_understanding`：`准确`、`部分准确`、`偏离`、`无法判断`；
- `root_cause_evidence`：`充分`、`薄弱`、`无`、`无法判断`；
- `patch_scope`：`最小聚焦`、`可接受`、`过度修改`、`无关修改`、`无法判断`；
- `verification_quality`：`覆盖目标与回归`、`仅目标验证`、`验证不足`、`未验证`、`无法判断`；
- `risk`：`低`、`中`、`高`、`无法判断`；
- `final_answer_faithfulness`：`如实`、`夸大`、`与轨迹矛盾`、`无法判断`。

每个标签必须包含：

- 简短理由；
- transcript 事件、diff 或测试输出中的证据引用；
- judge 配置版本。

证据不足时只能选择 `无法判断`。LLM judge 不判定补丁是否真正修复问题，也不能覆盖官方 evaluator 结果。

## 逐题配对与聚合

候选版本必须与固定基线在同一个实例清单、base commit、环境和 evaluator 版本上逐题配对。

每轮计算：

- `wins`：基线失败、候选通过；
- `losses`：基线通过、候选失败；
- `unchanged_pass`：两者都通过；
- `unchanged_fail`：两者都失败；
- `net_resolved = wins - losses`；
- 所有 outcome flip 的实例清单。

总体通过率只作为摘要，不代替配对结果。

效率指标按结果分层比较：

- `unchanged_pass` 用于比较成功路径的 token、耗时、费用、轮数和工具调用；
- `unchanged_fail` 只用于失败诊断，不用于宣称效率提升；
- outcome flip 单独展示，避免“更早失败”被误判为更高效；
- 聚合报告中位数和 P90，不只报告平均值；
- 额外报告总费用和每个 resolved 的费用。

## 回归结论

每个候选版本输出以下四种结论之一：

- `退化`：出现新的严重门禁违规；或 losses 大于 wins；或评测完成率下降；或逐题结果一致但关键成本越过预先配置的退化阈值；
- `改善（暂定）`：没有新的门禁违规，wins 大于 losses，且成本与风险没有越过退化阈值；
- `持平`：没有 outcome flip，门禁结果一致，关键成本没有越过预先配置的阈值；成本改善作为附加标签展示，不改变正确性结论；
- `无法判断`：wins 与 losses 相等且均大于零、存在影响比较的基础设施异常，或正确性改善伴随显著成本或风险恶化。

成本阈值必须在运行前配置并版本化，不能在看到结果后调整。首版不预设通用百分比，由项目根据基线分布确定。

关键版本应至少复跑全部 outcome flip，而不要求全量重复。复跑结果属于独立证据，不能覆盖或删除原始运行。

## 定性评审抽样

LLM judge 初审覆盖：

- 所有 wins；
- 所有 losses；
- 所有门禁违规；
- 所有异常停止；
- 从 `unchanged_pass` 和 `unchanged_fail` 中分别抽取固定比例或固定数量的样本。

人工复核覆盖：

- 所有 losses 和高风险项；
- judge 输出 `无法判断` 的实例；
- judge 与确定性证据冲突的实例；
- 随机抽取的一部分其余结果，用于监控 judge 漂移。

judge 必须固定模型、prompt、温度和 rubric 版本。输入中隐藏“基线”与“候选”身份，并随机化展示顺序，减少位置和版本偏见。

## 可复现性元数据

每次 run 保存：

- run ID、开始时间和结束时间；
- Agent commit；
- 模型提供方、模型版本和路由配置；
- system prompt、工具定义和运行配置的 hash；
- 实例 ID、仓库和 base commit；
- evaluator 与数据集版本；
- 环境镜像或环境标识、依赖锁版本；
- 随机种子；
- judge 配置版本。

缺失关键元数据的运行可以用于调试，但不能作为正式基线。

## 报告结构

顶层记分卡只展示：

- 已完成实例数与基础设施异常数；
- resolved 总数；
- wins、losses、unchanged_pass、unchanged_fail；
- 新增门禁违规；
- 总费用及成功路径的 token、耗时中位数和 P90；
- 回归结论。

下钻页面展示：

- outcome flip 清单；
- 每题官方测试结果；
- 过程指标；
- 补丁统计；
- 定性标签、理由和证据；
- 失败根因。

首版不生成总分或排行榜。

## 与现有实现的关系

`benchmark/metrics_table.py` 已收集 Agent 轮数、工具次数、重复命令、大结果外置、命令失败、token 和耗时。

首版主要缺口是：

1. 读取并规范化官方 SWE-bench evaluator 结果；
2. 记录门禁结果和补丁统计；
3. 保存完整的可复现性元数据；
4. 生成基线与候选版本的逐题配对报告；
5. 增加带证据的定性 judge 输出。

现有 CSV 可以继续作为导出格式，但规范化运行记录应保存为结构化 JSON；CSV 不适合作为带嵌套证据和版本信息的唯一事实来源。

## 验收标准

1. 同一批实例的基线和候选运行可以按 instance ID 配对。
2. 基础设施失败不会被计作 Agent 失败。
3. 官方 resolved 结果与本地汇总一致。
4. 任一严重门禁不能被成本改善掩盖。
5. 效率比较不会把更早失败判定为成功路径提效。
6. 每个定性标签都包含证据，缺证据时为 `无法判断`。
7. 报告可追溯到 Agent、模型、prompt、环境和 evaluator 版本。
8. 报告能输出 wins、losses、四类配对结果及四态回归结论。
9. 原始运行与复跑记录均保留，不互相覆盖。

## 测试策略

确定性单元测试覆盖：

- evaluator 报告到结果层字段的映射；
- infra error 与 agent failure 的区分；
- 门禁规则的命中、未命中和未执行状态；
- patch 行数、文件数和禁止路径统计；
- 配对矩阵与四态结论；
- 分层效率聚合；
- 缺失元数据时拒绝建立正式基线。

集成测试使用少量固定 fixture 覆盖：

- 基线失败、候选通过；
- 基线通过、候选失败；
- 双方通过但候选成本越界；
- evaluator 崩溃；
- 测试篡改；
- judge 无证据时返回 `无法判断`。

judge 评测使用人工标注的小型固定样本，检查标签一致性、证据引用和版本升级后的漂移，不用 judge 自己评判自己。
